# Domain Tooling, Graded Knowledge & Long-Horizon Execution

The `mindie-remote-dev` MCP tools are general remote tools, usable on demand in
any native task without invoking MindIE Agent. Supply or verify the actual host,
port, user, container and working directory. Poll the task's own returned job
handles and retrieve artifacts through remote-dev; reuse the full container ID.
Optional community capture has its own saved choice and project scope; remote
use does not activate or change it.

## 1. Graded Knowledge (`L1–L4`), Reference Identity, `knowledge_distill` & Paired-Runtime Boundary

- **Purpose Tier vs. Evidence Strength**:
  - `tier` (`L1` axioms & measurement probes, `L2` standard troubleshooting SOPs, `L3` convergence workflows, `L4` orthogonal exploration mutators) describes how a unit is used.
  - `evidence_strength` (`hardware_spec` | `reproduced_empirical` | `single_observation` | `hypothesis`) and `provenance` (`source_type`, `source_locator`, `source_digest`, `evidence_refs`, `supersedes`) describe how strongly it is supported. Never treat a `single_observation` or `hypothesis` as a hardware axiom.
- **Graded `knowledge_query` Parameters, Multi-Domain Routing & Response Shape (`graded-bm25`)**:
  - Parameters: `query` (nonempty search text), optional `domain` (explicitly selects the default domain or a registered `domain_configs` Engine/Feed such as `"vllm-ascend"` or `"operators"`; cross-domain references use existing `source_locator` / `evidence_refs` links rather than automatic federated retrieval), `limit` (`1..20`), `continuation` (for legacy related pages), `domain_path` (preferred `domain_path` prefix with cross-directory fallback), `token_budget` (`1..16000`, default `800`, covering body excerpts and inherited rules while excluding metadata), `include_unknown` (default `false`), and `include_archived` (default `false`; archived/superseded units remain addressable by exact ref but are excluded from ordinary discovery unless this is true).
  - When a graded corpus is installed (`retrieval: "graded-bm25"`, `page: "graded_units"`), the response carries bounded navigation `cards`, deduplicated `foundation_cards` (matched `L1` premises, once), compatibility `results[]`, and `usage` (`token_budget`, `estimated_tokens`, `body_token_estimate`, `estimator`, `has_more`, `excluded_budget`). Unknown conditions surface as `match_status="condition_unknown"` and `ready_to_apply=false` without expanding the body; `excluded_conditions` counts mismatched/unknown/archived omissions.
  - `results[]` items return:
    - `id` (stable path-independent `unit-...` ID),
    - `ref = "mindie://<domain>/units/<id>@<integer revision>"` (bound to the observed revision),
    - `unit_ref = "mindie://<domain>/units/<id>"` (stable unit URI without revision),
    - `feedback_ref = ref` (the same revision-bound URI for graded units),
    - `revision`, `match_status` (`matched` | `mismatched` | `condition_unknown`), `missing_conditions`, `tier`, `category`, `evidence_strength`, `domain_path`, `conditions`, `provenance`, `excerpt`, `excerpt_truncated`, `inherited_rules` (each with its own `ref`), and `inheritance_excluded`.
- **Graded `knowledge_explain(ref | refs, conditions, known_refs, token_budget)` & `knowledge_feedback(ref, rating=None, ...)` Routing by URI Authority**:
  - Pass query's readable `ref` (`mindie://<domain>/units/<id>@<integer revision>`) or `unit_ref` to `knowledge_explain(ref)`, and copy the exact `feedback_ref` to `knowledge_feedback(ref, rating)` (**never pass a bare `id`**; for graded units `ref` and `feedback_ref` share the same revision-bound URI value, whereas legacy material keeps task/block `ref` and `feedback_ref` distinct without mixing their roles). Both tools route to the target domain engine by parsing the URI authority (`mindie://<domain>/...`).
  - For a single graded unit, `knowledge_explain(ref)` returns `kind: "graded_unit"` with `ref`, `unit_ref`, `feedback_ref` (equal to `ref`), `id`, `revision`, `frontmatter`, `content`, and `inherits_from_closure`. It does **not** return legacy `first_block_ref` / `previous_block_ref` / `next_block_ref` navigation (those fields apply only when reading legacy task/block references).
  - Batch reads use `knowledge_explain(refs=[...], conditions=..., known_refs=[...], token_budget=4096)`: `units` are the requested complete, untruncated bodies; `requires` holds shared premises once in topological order; `unresolved` distinguishes `condition_unknown`, `condition_mismatch`, `budget_excluded` (with `required_tokens`), `removed_or_superseded` (with `superseded_by`), and `not_found`; `usage` reports the response budget. `known_refs` means exact `id@revision` refs still fully visible in the active context—not the session's read history; after compaction, re-read rather than assume visibility. A batch routes by its first canonical `mindie://` ref and must not mix domain authorities.
  - `knowledge_feedback` requires the exact returned revision URI (`feedback_ref` / `/units/<id>@<integer revision>` for graded units, or legacy `feedback_ref` for legacy material). `rating` is optional, so event-only feedback and vote+event calls are both valid. Optional `event_type` is `discovered` (query delivery) | `loaded` (explain full-body read) | `applied` (used in a run) | `evaluated` (bind `outcome`); `run_id` and `step_id` associate the event with a managed run, and `outcome` is `supported` | `refuted` | `inconclusive`. Events are idempotent by `(root_opaque, unit_id, revision, event_type, run_id)`.
  - When citing knowledge in reports or ledgers, record `id` (`unit_id`) and `revision`. Do not ask callers to compute or verify content, source, contract, or closure digests; informational digest fields, if returned, are not part of the public reference identity.
- **Three-Valued `conditions` Matching (`matched` | `mismatched` | `condition_unknown`)**:
  - Query evaluates the exact condition keys declared in each unit's `conditions` mapping (such as `soc`, `cann`, `driver`, `framework`, `repository`, `revision`, `workload_scope`, `dtype`, `input_shape`, or `workload_case_sha256`; never assume a hardcoded legacy condition-key list). Inherited `_common/` rules evaluate their own declared `conditions` independently and never widen applicability.
  - `condition_unknown` occurs when either a declared `required` premise on the unit or the caller's `observed` fact is `"unknown"`, missing/not supplied, or has an incomparable version/framework format, and `unknown == unknown` never matches (an absent requirement or `"any"` is unconstrained `matched`, and historical `required: "unknown"` is never backfilled by later machine versions). **Never** treat `condition_unknown` as `matched`—verify whichever fact is missing or unknown first (e.g., source `repository`/`revision` for an `L2` source SOP, or runtime environment for an NPU rule).
- **Explicit Selected-Evidence Distillation (`knowledge_distill`) & Multi-Domain Authorization Boundary**:
  - `knowledge_distill(inputs, task_state, domain=..., related_refs=[...], proposal=...)` distills caller-selected, already-authorized evidence into local C5 graded units for the default or explicitly selected `domain` using that domain's active task capture lease and configured native organizer (`SummaryLedger`). Writing/distilling to a non-default registered `domain` requires that target domain's own existing `consent` and `project_root` scope plus explicit target activation (`bridge.py activate --domain <domain>`); ordinary reads never widen authorization.
  - `inputs`: non-empty list of evidence objects (`<= 256 KiB` total serialized), each requiring `kind` (`experiment_ledger` | `run_manifest` | `authorized_transcript` | `ecosystem_repo` | `hardware_spec` | `ablation_receipt`), `outcome` (`observed` | `verified` | `compile_failed` | `infra_failed` | `measurement_invalid` | `in_flight`), `source_locator`, `content`, `evidence_refs`, and optional `repetitions` (`>= 1`).
  - **Milestone/delta/proposal**: `task_state`: `"in_flight"` | `"verified_milestone"` | `"completed"`. Invoke `knowledge_distill` at `verified_milestone` or `completed`; an `"in_flight"` task may also distill a genuinely verified milestone item. `observed` as well as fault/environment/build evidence (`compile_failed`, `infra_failed`, `measurement_invalid`) can be distilled into `single_observation` or `hypothesis` (preserving its true `evidence_strength` without elevating unverified fault/build evidence to `hardware_spec` or `reproduced_empirical`; `hardware_spec` specifically requires a `hardware_spec` source, `reproduced_empirical` specifically requires `outcome == "verified"` with `repetitions >= 2`, and `L4` specifically requires a verified `mindie-bench-ablation/1` receipt). Optional `related_refs` names same-topic old units (`unit_id` or graded refs) so the organizer sees a delta and prefers revise/merge/supersede over a duplicate unit. Optional `proposal` is a caller-formed `mindie-distill-decision/1` object that is deterministically validated and applied with `model_calls=0`. Only `task_state="in_flight"` without a verified milestone (or all-`in_flight` / empty inputs) is a deterministic zero-call `noop`, and an ordinary host `Stop` event never implies task completion. If a local receipt or application step fails after the native model returns, the completed decision is preserved (`operation_status="local_receipt_failed"` or `"local_application_failed"`, `local_error`) and the paid model call is **never** automatically replayed.
  - **Paired-Runtime & Release Boundary**: `knowledge_distill`, multi-domain routing, and the graded `knowledge_query` options (`domain_path`, `token_budget`, `include_unknown`, `include_archived`) plus progressive `knowledge_explain(refs, known_refs)` and usage-event feedback require the paired `mindie-knowledge 0.13.0` runtime. It supports graded Git publication (`mindie-publication-contract/2`), independent Feed sync, and revision-bound unit feedback (`feedback_ref` / `/units/<id>@<integer revision>`). The selected feed revision and installed runtime identity are separate facts; use their own receipts to verify them.

### 1.1 Progressive Loading, Experience Flywheel & `P0`–`P3` Contract

- **`P0` two-step loading**: call `knowledge_query` with observed `conditions` and read only its bounded `cards` + `foundation_cards`. Choose the few units that can change the next decision, then call `knowledge_explain(refs=[...], conditions=..., known_refs=[...], token_budget=4096)` once for the whole batch. Query excerpts are navigation, not the decision body; explain returns complete bodies and shared premises once. `known_refs` is the exact set of `id@revision` refs currently fully visible, so post-compaction state must be re-established rather than assumed. If `unresolved` reports `budget_excluded`, raise the budget, narrow the question, or read the prerequisite first; never pretend a truncated step is complete.
- **`P1` experience connection**: at a verified milestone use `related_refs` for same-topic delta comparison, then record `applied` with the managed `run_id`/`step_id`. When a run has a judgment, record `evaluated` with `outcome="supported"|"refuted"|"inconclusive"`; the four usage stages are `discovered` → `loaded` → `applied` → `evaluated`. Delivery is not adoption, and adoption is not validated benefit; counters derive from deduplicated events, never a model-written success total.
- **`P2` contraction**: prefer revise/merge/supersede/archive over creating another near-duplicate. Keep the old unit addressable by exact ref, and let superseded/archived units leave ordinary discovery (`include_archived=false`). Distillation `related_refs` supplies the delta basis; a `proposal` can express the merge/replace decision deterministically.
- **`P3` exploration and rewrite-back**: a verified exploration result returns at the right granularity—hardware/invariant limits as `L1`, diagnostic procedures as `L2`, branch-selection experience as `L3`, code transformations as `L4`. Preserve verified sub-findings and open hypotheses when resources run out; do not declare an entire direction failed.

## 2. Diagnosis and exploration

Knowledge tiers describe use, not a mandatory execution order. Apply complete,
condition-matched prerequisites; select L3 branches from observations. Hermes
can revise any tier, and an exploration finding may be L1, L2, L3 or L4.

Read [Diagnostic Reasoning](diagnostic-reasoning.md) when the routine path no
longer explains the evidence, accuracy depends on state/observation, or a
milestone challenges existing knowledge. It covers discriminating experiments,
first divergence, observer controls, sequence reproducers, independent oracles,
and preserving corrections. Keep evidence validity, goal attainment and
reusable information distinct. Repeated no-information attempts prompt review;
new facts are progress even without a performance improvement.

Use `task_state="verified_milestone"` for a finished sub-result in a continuing
task. `in_flight` and all-pending inputs remain no-op; Stop is not completion.
Keep supported/refuted/inconclusive judgments with their scope and source.
Only L4 transformation admission requires the verified final-combination
ablation receipt; diagnostic findings need the evidence appropriate to their claim.

## 3. Long-Horizon Continuation Ledger (`PROGRESS.md` + `experiment-ledger.jsonl`) & Sequential Ablation

Long-horizon optimization and 0-Day model adaptation reuse `coordinator`'s authoritative `Run Manifest` (`run_id`) rather than inventing a second task state machine:

- **1. Launch-Time `run_id` Registration (`in_flight_runs`) & Atomic `PROGRESS.md` Maintenance**:
  - `coordinator` assigns `run_id` (`run_id == execution_id`) at submission time (`client.run`), and a submitted `run_id` is never replaced.
  - **Immediately upon launch** (before polling or ending the turn), atomically replace `PROGRESS.md` (`os.replace` / full-file write) to add `{run_id, job_id, slot_id, host_endpoint, manifest_path, started_at}` under `in_flight_runs`.
  - **Long-task recovery facts (use the existing task record; simple tasks need no extra ledger)**: (1) Goal, acceptance criteria & remaining budget; (2) Current workspace `git_commit`/`diff_digest` vs. **verified baseline `run_id`** vs. **best verified candidate `run_id`** (never conflate unverified edits with verified runs); (3) Remote endpoint & last verified environment timestamp; (4) Active `in_flight_runs`; (5) Active hypothesis & next minimal experiment; (6) Key historical `conditional_avoid` references (`exp_id` + `run_id`) that still constrain decisions beyond the recent context window.
- **2. Recovery-First-Query Protocol (Zero Duplicate Submission on Compaction/Resume)**:
  - On any context compaction, turn interruption, or session resume, **read `PROGRESS.md` `in_flight_runs` first** and query the original execution via `TaskClient.observe(run_id=...)` or `remote_job_status(job_id=...)`.
  - Only move a `run_id` out of `in_flight_runs` after its terminal `Run Manifest` receipt is observed and recorded. Never submit a new execution to replace an active or uncertain in-flight `run_id`.
- **3. Single-Writer `experiment-ledger.jsonl` & Sequential Pruning Consumer Rule**:
  - **Execution Facts (`Run Manifest`)**: Owned by `coordinator` (`passed` / `failed` / `inconclusive` / `cancelled`; `unknown` reserved strictly for uncertain external writes). Local ledger/receipt write errors must be reported separately and must **never** overwrite a succeeded remote execution result.
  - **Hypothesis Judgments (`experiment-ledger.jsonl`)**: Append one JSON object per experiment via the single task entry point:
    `{"task_id", "exp_id", "run_ids": [...], "hypothesis", "factors": [...], "factor_roles": {"<f>": "performance|correctness_required|dependency|inseparable_group"}, "unit_refs": [{"unit_id", "revision"}], "receipt_refs": {"manifest", "profile", "ablation"}, "run_status", "judgment": "supported|refuted|inconclusive", "scope_conditions": {"soc", "cann", "dtype", "shape_family"}, "conditional_avoid": "...", "supersedes_exp_id": null}`.
  - Compile errors, SSH drops, or invalid measurement windows record `judgment: "inconclusive"` (never domain `refuted`). When hardware, shapes, or preconditions change, earlier `conditional_avoid` directions may be re-tested by setting `supersedes_exp_id`.
  - **Contract C4 Consumer Rule (`candidate_for_sequential_pruning` -> RETAIN)**: Leave-One-Out (`LOO`) `delta <= tolerance` only marks a factor `disposition: "candidate_for_sequential_pruning"` and **never** auto-deletes it. You **must** treat `disposition == "candidate_for_sequential_pruning"` with `pruned_combination_verified == false` as **RETAIN**. Only prune factors verified by sequential one-at-a-time `pruning_runs` where the final combination passes both `correctness_verified` and `performance_verified` (`pruned_combination_verified == true`). `L4` distillation requires a verified ablation receipt (`baseline_run_id` + `verification_run_id`).

## 4. Pre-Compilation Parallelism, Physical NPU Timing Mutual Exclusion & Profiler Discipline

- **Parallel Ideation & CPU Pre-Compilation (`npu_count=0`)**: When parallel work is authorized, confirmed device-free steps may run concurrently using per-slot cache directories (`MINDIE_SLOT_ID`, `ASCEND_CACHE_PATH`, `TORCHINDUCTOR_CACHE_DIR`, `TRITON_CACHE_DIR`). Select the next experiment for its discriminating observation; use native isolated context only when supported and authorized, preserving current facts and conditional counterevidence.
- **Exclusive Physical NPU Timing Lease**: Any performance benchmark, attribution check, or `mindie_profiler` collection on the same physical NPU (or same Ascend A3 dual-Die package) must acquire an exclusive `coordinator` timing lease and drain `/proc` process trees before the next run starts.
- **Layered Profiling & Honest Narrowings (`mindie_profiler`)**:
  - **Explicit Unlabeled or Labeled Windows (`segment.py`)**: `python -m mindie_profiler` supports **explicit unlabeled time windows** (`--time-window START:END` / `--window START:END`), **explicit labeled step windows** (`--step-window STEP=START:END` / `--step STEP=START:END` / `--steps-file`), and explicit `--full-range` (in `--unit us|ns|ms`). Not every analysis requires step labels, and `mindie_profiler` **never** infers real step identity from kernel rows, timestamps, or CSV headers.
  - **Explicit Scene Annotations & `clock_domain`**: Scene metadata (`--mode`, `--framework`, `--phase`, `--tp`, `--dp`, `--graph-mode`, `--clock-domain`, `--input-signature`) uses explicit caller annotations and reports `uncertain` otherwise (`scene_detector.py` never infers hidden runtime state from kernel rows). Without `--clock-domain`, multi-rank DB analysis emits `measurement_limitation: "clock_domain_unknown"`, and `compare.py` refuses cross-run timing comparison unless `clock_domain` matches.
  - **Non-Additive Time Views & `slowest_rank`**: `busy_union` (overlap counted once) and `kernel_sum` (per-event sum) are deliberately non-additive (`host_gap = wall - busy_union`, `exposed_comm = comm_union - noncomm_union`); `slowest_rank` is selected by wall `p50` across 7 semantic blocks (`Attention`, `MoE`, `Comm`, `Norm`, `Copy_Layout`, `Host_Gap`, `Unclassified`).
  - **Three-Time Separation & Unverified `msmodeling` Provider (`theoretical_model.py`)**: Keep `ideal_hardware_lower_bound_ms` (local `roofline-max-v1` single-kernel bound, **not** a whole-network bound), `model_predicted_ms` (populated **only** when a validated external provider with real version, matching protocol, matching `input_signature`, and non-empty evidence is injected; otherwise `None` with `unmodeled_reason`), and `measured_device_ms` strictly distinct. `probe_msmodeling_adapter` reports install state only and never imports or executes `msmodeling` (`verified=False`, real `msmodeling` provider remains unverified).
  - **No `85°C` Throttling Heuristic**: `>= 85°C` is an observation only (`used_as_throttling_proof=False`). Only explicit hardware/telemetry throttle signal bits prove throttling; missing signals are recorded in `measurement_limitations` (`throttling_detected=False` without signal coverage is not proof of no-throttle).
