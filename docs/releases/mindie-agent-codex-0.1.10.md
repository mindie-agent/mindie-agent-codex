# mindie-agent-codex 0.1.10

本版本修复旧安装无法完成空闲升级的问题：`tools-mcp` 空闲时不再持有更新锁；原生安装的新 MCP 启动器可以迁移仍指向 0.1.8 / 0.1.9 的旧绑定；中断的本地激活及已被原生管理器清理缓存的旧候选不再永久阻塞后续检查。

## 修复内容

- 入口完成 profile 校验后退出共享锁，再启动常驻 MCP。真实工具调用仍在执行期间持锁，调用结束后释放。
- 新版 MCP seed 在启动时进入新版迁移控制器，等待旧调用和服务空闲后，通过现有原子切换路径发布完整解释器、脚本与配置绑定。Hook 命令保持稳定；Stop 不触发迁移。
- 激活子进程通过标准输入接收不可变的尝试快照。即使父进程的待处理回执被替换，延迟到达的旧子进程也不能把新绑定降级。本地中断由绑定读回恢复，结果未确认的原生安装或市场写入仍不重放。
- 原生安装器删除旧版本缓存后，已完成准备的旧候选仍可依据已验证回执归档。修复 macOS 文件锁忙错误码与 Linux 不同导致的并发启动失败。
- MCP 启动预算为 2760 秒，覆盖基线准备、组件继承、旧调用排空与迁移；远端工具 720 秒、组件工具 330 秒的宿主调用预算及环境变量透传保持原合同。

## 验证范围

本地最终合同测试：598 项测试、493 项子测试通过；26 项跳过，2 项 live NPU 测试未运行。macOS、Linux、Windows CI 对同一提交执行全部组件合同测试；正式发布流水线另行校验依赖 Release、执行测试与微基准，并随包提供报告和校验和。

在 macOS 的实际 Codex Desktop `0.164.0-alpha.11.1` 中，以私有配置和真实已发布 0.1.8 运行时、原生安装的 0.1.9 候选出发，原生安装候选源码并刷新同一聊天。验收在约 47 秒内确认：两个 MCP 均加载 0.1.10，目录包含 22 个远端工具和 5 个组件工具，canonical 绑定完整切换，空闲排他锁可用，用户字段及贡献授权保持不变；正常后台循环归档旧候选并继续 Release 检查。候选尚未发布时，Release 选择如实返回没有更高的兼容正式版。

这项发布前验收使用隔离候选源码，不等同于正式发布后的后台发现。原生管理 API 的 `mcpServer/tool/call` 不携带真实 turn 身份，验收确认该调用被拒绝，没有手工注入身份来伪造业务调用。运行时组件 CLI 的无损状态检查通过；用户真实 turn 的工具调用与实际宿主加载状态需在发布后分别核验。另一个实际宿主探针验证了刷新期间旧调用完成后再退役旧连接。

## 首次升级边界

已经常驻的 0.1.8 / 0.1.9 更新器无法自行载入修复。若它已卡在旧激活回执，首次恢复需要原生安装器先选中本正式 Release 的精确源码，再通过宿主支持的 MCP 刷新或自然重载接入新版。旧市场目录未更新时，重复 `plugin add` 仍会重装旧版本。不要通过修改版本号、删除锁或覆盖运行时文件绕过迁移。

原生安装、运行时准备、canonical 生效和宿主加载新工具分别读回；只完成前两项不能报告升级已经生效。保存的用户授权继续复用，知识仍仅在手动 `/mindie-agent` 后按会话启用。
